## The defect
`dla harness gen --lang node --driver` writes `agent/dla-preload.js` and `driver/dla-harness.js`
(CommonJS) under `.dla/<run>/harness/H<n>/`, inside the project's scratch copy. When the
project's package.json has `"type": "module"`, Node loads every `.js` under it as an ES module
and the run dies with `require is not defined in ES module scope`. Command mode (`--require
.../dla-preload.js` on the project's own command) fails the same way. No bench fixture has
`"type": "module"`.

## Wanted
1. The agent and the driver load whatever the package type is. The straightforward way: write
   them as `dla-preload.cjs` and `dla-harness.cjs` always (a `.cjs` file is CommonJS in any
   package) and update every reference: `crates/dla-workload/src/harness/{gen,commands,templates,mod}.rs`,
   `harness/node/README.md`, the skill references that name the files
   (`skills/detect-leak-anywhere/references/node.md` and any other; grep), `dla-bench`'s fixed
   policy for node fixtures (`crates/dla-bench/`, grep `dla-harness`), tests and docs. If you

   generated by an older version (files named `.js`) must still run: `dla harness run` uses the
   names recorded in `harness.json`, do not break that.
2. Hooks can load ES modules: next to `projectRequire(file)` the driver gets
   `projectImport(file)` (dynamic `import()` of the file URL; hooks are already async). The
   comment above the hooks says which to use; when the project's package.json says
   `"type": "module"` (or the target's file is `.mjs`), the generated target block says so.
3. Probes of module-level bindings in ES modules. Today the agent exposes the top-level
   bindings of probed CommonJS modules through `Module.prototype._compile`
   (`harness/node/dla-preload.js`, about line 570). For an ES module that does not run. Use
