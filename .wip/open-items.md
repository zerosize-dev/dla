## Budget, time and reasons

- **problem** `crates/dla-cli/src/gate_hooks.rs:779-791 with crates/dla-core/src/toolctx.rs:120 (refused_since: `worker.is_none() || by == worker`)`

  The core's Stop hook (budget_note called with worker None) counts a worker's `none_fits` refusal as if the core had been refused. A worker that reaches its own deadline is refused by `require_time` with `none_fits: true, worker: <name>` (toolctx.rs:419). With 2 or more workers, each worker's share ends at about 42% of the budget, so this happens in an ordinary dispatched run while most of the run budget is left. Reproduced end to end with target/debug/dla in a scratch run: an interactive run (`run init --budget 60m`, `dla consent --tiers 1,2`), then `run dispatch --workers python,go` with go's deadline moved into the past, then `dla --worker go sample --pid N`. That refusal wrote `{"none_fits":true,"worker":"go"}`. The core Stop hook then changed from "59 of 60 budget minutes remain: measure what is open instead of stopping." to "59 of 60 budget minutes remain, too few to start another measurement: ask the user once whether to extend the budget (dla run extend <dur>); if the user declines or does not answer, close what is open...". An unattended core is told to close what is open instead. This contradicts decision 3 (never ask or close while more than the floor is left). SKILL.md:121 and recovery.md:124-127 speak of the core's own command being refused, and stages.md:163 tells the core to re-test a worker's time_budget findings while run time is left. The hook gave the right text before this refix. Fix: in the core, count only refusals whose `worker` is null (match `by == worker` exactly in nothing_fits_since), and add a gate_hooks case with a worker's none_fits line.

## Coverage warnings and harness steps

- **problem** `crates/dla-core/src/gate.rs:1709-1721 (hook_driver_in takes the first hook driver) with the new branch at gate.rs:1774-1783 (driver_step); docs/VERIFY.md:506; crates/dla-cli/tests/keep_going.rs:886`

  An older hook driver whose build failed still hides a newer hook driver that ran. Case ADV-A: H1 is a hook driver whose last attempt is `failed`/`build_fails`, and a newer hook driver H2 built and ran 750 iterations, reaching 0 of 225 entry points. build_failed_harness returns None because H1 is older than H2. hook_driver_in picks H1, and the new X1 branch then returns H1's build step. The gate fix, the Stop hook (seen) and the report's Coverage warning all say "harness H1 did not build ...: fix the build error that `dla harness run H1` prints ... or record the blocker ... --reason build_fails". None of them names H2, the driver whose hooks need filling. The build_fails escape it offers is also false, because H2 built. ADV-A2 (H2 reached 20 of 225) gives the same step in the warning. Before refix 2 this case said "fill the DLA-HOOK bodies of H1", which was also wrong, so this is not a regression. But row 506 claims "an older failed build never hides the hook driver that ran later", and the test `an_older_build_failure_does_not_hide_the_hook_driver_that_ran` covers only a command or JUnit H1, so neither the code nor the test holds that claim. A realistic way to reach this state: the model fills H1's hooks with code that does not compile, then makes a new driver with `gen --driver`. ## JVM non-heap verdicts and CodeQL

- **problem** `crates/dla-cli/src/alloc_cmd.rs:655-662 (agent_drift keeps only required columns whose plateau reads continues), with the caution text at :687-688`

  The refix to item 1 brings back P7 item 1 for a thread leak that does not add a thread at every checkpoint. I reproduced it on real JVMs with the current binary: r3/sn2 and r3/sn3 in a scratch run The driver unit starts a daemon thread when `i % 10 == 0` (sn2) or `i % 15 == 0` (sn3), with step 5, 20 iterations and no `dla trend`. With no trend, jvm.threads and os.threads are required. Both read plateau `inconclusive`, with net rises of 10 (sn2) and 6 (sn3) threads over the extra window, and jvm.nonheap_used rose 392 and 343 KB. split_rising drops the thread columns, so the result is the agent-drift override: verdict inconclusive, a caution that says "no jvm.nmt.* category or thread count rises" (false: the thread count rose 10), and `next` = `dla harness gen --lang jvm --driver --step <larger>`. No limitation names jvm.threads: held_back and open_columns are empty because the verdict was leak before the override. The previous code (rising_required, every required column that is not non-leak) gave Growing for this case: threads named, leak kept, thread capture in `next`. A thread count is a counter with no checkpoint jitter: idle drivers r/nt1 to nt3 read jvm.threads at plateau with rise 0. So any net rise is growth, but the plateau test reads `continues` only when every delta is at least 1. Fix: count a required jvm.threads or os.threads with a positive net extra rise (or one over a small jitter, as for classes) as rising, and keep the continues-only rule for the jvm.nmt.* byte categories. Add a unit case: jvm.threads inconclusive with extra_rise 10 must not return Drift::Agent.

- **problem** `crates/dla-cli/src/alloc_cmd.rs:644-654 (Drift::Classes is returned before the required-column check at :655-686); crates/dla-cli/tests/alloc_test_jvm.rs:599`
