Go candidates are ordered so a holder fed from many places comes first, and a package of a nested module can be driven

From the miss on a Go library of 32 modules in the unattended test on
projects the tool had never seen. The model gave up after 7 minutes of a 3
hour budget: most packages are in nested modules and the generated driver
could not be built for them, and its first "leaks" were test helpers. The
documented leak, a slice field appended in fourteen methods and reset in
one, was listed at rank 118 of 149; fifteen registration rows with no
writer scored higher, and twelve of the first forty ranks were packages of
test helpers.

THE SCORE

- `w_many`: a holder added to from three or four distinct functions at run
  time gets +8, from five or more +16 (`w_many_lots`). Initialisers and
  start-up sites do not count.
- `r_reset_only`: +15 when every removal is a reset of the whole container
  and something adds at run time. Between two resets nothing bounds it.
- `go_support_dir`: -25 for a Go file in a directory whose name ends in
  `test` and is longer than that, the language's convention for a package
  of test helpers. A penalty, not a demotion: a project whose own code
  lives there keeps its order. A short list of English words that end in
  `test` (`latest`, `contest` and the like) is left alone.
- The Go census counts an exported method of an unexported type as
  exported: it is reachable through the interface the type implements.

On a copy of that library the slice moved from rank 118 to rank 66 (score
61 to 92) and is the second member of the first batch of its package;
test-helper packages in the first forty ranks fell from 12 to 2.

A PACKAGE OF A NESTED MODULE

- The module of a Go driver is the module of its package, the nearest
  `go.mod` at or above it. The driver is built and run there and the
  package is named relative to it.
- A work copy with more than one `go.mod` and no `go.work` of its own gets
  one at its root that lists every module directory, with the highest
  `go` directive, so the modules of the repository resolve from the copy.
  A copy cut to one scope also holds the modules the package's module
  needs from the repository.
- Coverage covers every module of the workspace that the driver links.
- A package whose only non-test Go files are generated is refused with
  that reason; `--next` goes on to the next package and names the skipped
  one in `_attention`.

On the copy of the library, with hooks that do nothing, drivers for
packages of two nested modules build, run, write a series and give `dla
trend` its coverage. Before, the first answered that the directory "holds
no Go package to drive".

Also: test scenes and texts that echoed names of the library's sources use
neutral names.

The whole dynamic acceptance passes: 63 of 64 fixtures and the expected
failure. The static acceptance passes on all 64.

Not covered. Hooks that reach the targets were run on a synthetic
repository only. A project's own `go.work`, vendor directories and a
module that needs a newer Go than the installed one (the `go.work` takes
the highest directive and the toolchain download fails offline) were not
tried. `--probe F` without `--package` still picks the package by census
count, not from the finding's site.
