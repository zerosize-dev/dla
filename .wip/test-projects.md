Each entry was proposed by one research pass and checked against its sources by a second one
(repository, issue, fix, tags). Nothing here was built or run. "Confidence" is the checker's.

## Kotlin and Spring Boot

### Spring Data Commons TypedPropertyPaths cache leak (Kotlin property references) (known leak, confidence medium)
- Repository: https://github.com/spring-projects/spring-data-commons (Core Spring Data module pulled in by every Spring Data Boot app; star count not read)
- Leak (heap (unbounded static cache)): Each call of Update().set(CounterDocument::counter, x) with a Kotlin property reference adds an entry to the static TypedPropertyPaths.resolved cache, because Kotlin creates a new capturing adapter per call and identity equality made every lookup a miss. Reporter output: cache size 10 after 10 calls, 10,000 after 10,000.
- Trigger: Loop of Update().set(KProperty reference, value), e.g. repeat(10_000). Reproducer needs no running MongoDB: https://github.com/damianmalczewski/spring-data-memory-leak (Gradle Kotlin DSL, ./gradlew run, pins spring-data-mongodb 5.1.0 and spring-data-commons 4.1.0). Reported on Spring Boot 4.1.0, Kotlin 2.4.10, Java 25.
- Issue: https://github.com/spring-projects/spring-data-commons/issues/3521
- Fix: https://github.com/spring-projects/spring-data-commons/commit/82479c59e315e74d449e740f0f8cceb146571f21
- Last version with the leak: 4.1.1 (tag exists, Aug 20 2026; reporter saw it on 4.1.0, tag 4.1.0 also exists)
- First fixed version: 4.1.2 (milestone 4.1.2 / 2026.0.2; tag 4.1.2 exists, Oct 22 2026)
- Why it fits: Kotlin-specific leak that a repeated call triggers in a few lines, no external service, a tiny reproducer. Fits a detector that loops an entry point and measures heap growth. Also a good test for explaining a growing static map.
- Build and run: Gradle with wrapper. Reproducer: ./gradlew run, prints cache size. For the library itself: Gradle/Maven build of spring-data-commons, JUnit 5 tests with no external service. Easiest path is the reproducer with the dependency version pinned to 4.1.0 versus 4.1.2.
- Researcher's caveats: Issue was closed 'fixed via #3546', but PR #3546 was closed unmerged; the commits were re-applied to main (82479c5, 7dc0f3a, 48ff3d8, 504fafe) and cite it. I did not confirm that tag 4.1.2 contains these commits (the page did not say); check with git tag --contains. I did not verify that 4.1.1 still leaks. Reproducer repo has 0 stars and is archived. The popular project is Java, not Kotlin; the Kotlin part is the caller.
- Checker's corrections: Issue #3521 was reported by Patryk-Piechaczek, not damianmalczewski (damianmalczewski only owns the archived reproducer repo that links the issue). The 'Reporter output: cache size 10 after 10, 10,000 after 10,000' is from the reproducer README/design (reflection sum of resolved map sizes), the issue itself states 10,000 calls gave 10,000 entries. Tag 4.1.2 does contain 82479c5 (compare page: 'up to date'), so that caveat is resolved, though the page cannot distinguish identical from ancestor; the follow-up commits of Oct 12 ('Ignore internal Kotlin types when resolving TypedPropertyPaths') were not individually checked against the tag. 4.1.1 was not run, but it predates the Oct 9 fix, so it should still leak (unverified by execution). Test the reproducer with spring-data-commons overridden to 4.1.2: note spring-data-mongodb 5.1.0 may still resolve it transitively, so pin commons explicitly (the reproducer already pins 4.1.0 directly, so just change that version to 4.1.2).
- Practical notes: Easiest: reproducer with ./gradlew run; needs JDK 25 (jvmToolchain(25) will try to auto-provision via Gradle toolchain download, which needs network access to a foojay/JDK vendor host and Maven Central; offline or sandboxed runs fail unless JDK 25 is preinstalled or the toolchain is lowered, e.g. to 21 or 17 if Kotlin 2.4.10 and Spring Data 4.1 permit; not verified whether Spring Data 4.x requires JDK 17 or newer, README says 17+). Kotlin 2.4.10 / Gradle wrapper version downloads also need network. Runs in seconds, 10,000 iterations, tiny heap; no services. Leak is small per entry (about 10 objects per call per reporter, 115k objects in production), so a detector loop needs many thousands of calls. Building spring-data-commons itself: ./mvnw clean install with JDK 17+, Maven; heavy full build (many modules/tests, tens of minutes), most unit tests need no external service but some modules/integration tests may; not verified. Popular but the leak library code is Java; the Kotlin part is only the caller in the reproducer. The fix is a source-level change in Java (SerializableLambdaReader) so a static analyzer for kotlin-spring would need to cover Java library code or the Kotlin call site only. Reproducer repo is archived (read-only but still cloneable). All dates are in the sandbox's 2026 timeline.

### Spring Boot devtools Restarter keeps contexts across tests (known leak, confidence medium)
- Repository: https://github.com/spring-projects/spring-boot (Most used JVM server framework; star count not read)
- Leak (heap (application contexts retained; classes/metaspace follow)): Restarter.rootContexts (a CopyOnWriteArrayList) gets every test's application context added and never removed, so contexts pile up across @SpringBootTest tests, even with spring.devtools.restart.enabled=false and a small spring.test.context.cache.maxSize. Removing devtools fixed it for the reporter.
- Trigger: Repeat @SpringBootTest tests (reporter used @DirtiesContext BEFORE_EACH_TEST_METHOD, RANDOM_PORT) with spring-boot-devtools on the test runtime classpath. This matches a detector that loops the project's own JUnit tests. Workaround: Restarter.clearInstance() after each test.
- Issue: https://github.com/spring-projects/spring-boot/issues/37373
- Fix: https://github.com/spring-projects/spring-boot/commit/1f0e311cb885f52fcc01a1a049f841a241db4a34
- Last version with the leak: v2.7.16 (tag exists, Sep 21 2023)
- First fixed version: v2.7.17 (tag exists, Oct 19 2023; issue milestone 2.7.17). Fix commit 1f0e311 'Completely disable restart when running tests'.
- Why it fits: Real leak found by looping tests. The fix is small (4 files). Spring Boot is the ecosystem the user cares about.
- Build and run: Gradle build of spring-boot (large; build only the spring-boot-devtools module and its tests). Tests run without external services. To test the detector on a Kotlin app instead, take any Kotlin Spring Boot Gradle app with several @SpringBootTest classes, pin Spring Boot 2.7.16 and add devtools to test scope.
- Researcher's caveats: Project is Java, not Kotlin. Issue reproducer used a PostgreSQL container, but the leak does not depend on it; no standalone reproducer is given. I did not verify that tag v2.7.16 still has the leak; the issue page lists no explicit affected versions, only a link to the 2.7.15 docs. Building the 2.7.x Gradle build today needs an old JDK (likely 8 or 17), not checked.
- Checker's corrections: Star count is 81.9k, forks 42.7k. I could not confirm 1f0e311 sits inside the v2.7.16..v2.7.17 range (the compare page timed out, 96 commits). The release notes list #37373 in 2.7.17, so the 2.7.x backport is probably a different hash from 1f0e311, which may be the commit on a newer branch. Use the 2.7.17 tag itself as the fixed ref rather than relying on that hash. I did not independently check the v2.7.16 tag date (Sep 21 2023) or the v2.7.17 year. v2.7.16 is confirmed to lack the fix by reading the source at that tag. The issue lists no affected versions, so the leak is not confirmed to exist specifically at v2.7.16 beyond the missing fix. Note the fix only prevents the leak when restart is implicitly disabled in tests, so the leak is not reproducible if the detector's runs set spring.devtools.restart.enabled=true.
- Practical notes: Not tested here (read-only research). The 2.7.x Gradle build is large; build only spring-boot-project/spring-boot-devtools and run its tests, which should need no external services. Spring Boot 2.7.x builds with JDK 8, 11 or 17 and uses the bundled Gradle wrapper. A newer JDK such as 21 is likely to fail, and I did not verify the exact JDK. It needs network access to Maven Central and the spring.io repos for dependencies. The upstream devtools unit tests may not exercise repeated @SpringBootTest loops, so the leak may not show there. A more faithful test is a small Spring Boot 2.7.16 app (Kotlin or Java) with spring-boot-devtools on the test runtime classpath and many @SpringBootTest classes or @DirtiesContext methods, compared against 2.7.17. No PostgreSQL container is needed for the leak itself; the reporter's container was incidental. The leak is caused by retained application contexts, so memory growth is visible after repeated tests with the heap capped.

- Trigger: Not read. Presumably repeated client requests with the retry plugin installed; unconfirmed.
- Issue: https://youtrack.jetbrains.com/issue/KTOR-5099
- Fix: https://github.com/ktorio/ktor/pull/3316
- Last version with the leak: not found (a 2.1.x or 2.2.0 tag likely, but not verified; the tags pages I could load do not show those tags)
- First fixed version: not found; fix merged to main Dec 14 2022 as merge commit 20099e0 (PR commit d6d6c5b)
- Why it fits: Kotlin repo, test-loop-able, but it is a Ktor client plugin, so it is a fallback because the area asks for Spring Boot first.
- Build and run: Gradle multi-module; large build, JUnit tests for the client modules, no external services expected (not checked).
- Researcher's caveats: The YouTrack page did not load, so the leak description, affected version and fix version are unverified. Need to find tags around Dec 2022 (tags?after=2.3.12 page). Weakest known-leak candidate; the reviewer on the PR asked for an allocation benchmark, so the PR may have no leak test. Ktor is not Spring Boot.
- Checker's corrections: affected_ref: 2.2.1 (the last tag before the fix merge; 2.2.0 and the 2.1.x tags are also affected, since the retry plugin dates from 2.0.0). fixed_ref: 2.2.2 (release notes name KTOR-5099). Tag dates: 2.1.3 Oct 26 2022, 2.2.0 and 2.2.1 Dec 7 2022, 2.2.2 Jan 3 2023. The newest tag "3.6.1 (Oct 29 2026)" was not confirmed: the repo page showed no releases and I did not look at the top of the tags page. Stars: 14.6k. leak_kind: heap, leaked coroutine Job objects (a child Job never completed). I did not confirm whether the leak shows up only after retries or on every request. I did not search for open leak issues because this is a known-leak candidate, not a control.
- Practical notes: Gradle multi-module build and a large repo. The 2.2.x line is from late 2022, so it likely wants JDK 8-11 (JDK 17 may work); the toolchain was not checked, so check the build files at tag 2.2.1 and 2.2.2. A trigger would only need ktor-client-core plus the mock engine (ktor-client-mock) with HttpRequestRetry installed, so there should be no external services. Run it as a loop of requests with retry enabled and watch Job and coroutine object counts. Practical risks: no leak test exists, so the tester must write a workload. The diff is only about 7 lines, so the leak is subtle for a detector, and the Job is a child of the request execution context, so heap growth may only show if the parent context is long-lived (not verified). The leak is in common Kotlin multiplatform code, not Spring, so it is a fallback if a Spring Boot target is wanted. A full Gradle build of the whole repo is slow, so build only :ktor-client:ktor-client-core and the mock engine. Network is needed for Gradle dependency downloads.

### Eclipse Jetty: GzipHandler leaks Inflater per gzip request (CVE-2026-1605) (known leak, confidence high)
- Repository: https://github.com/jetty/jetty.project (4.1k GitHub stars (repo page); embedded server used by Spring Boot, Javalin and others)
- Leak (off-heap or native (java.util.zip.Inflater objects never released)): GzipHandler creates a GzipRequest and its inflater, but the callback is wrapped only when both inflation and deflation are needed. If the response is not deflated, destroy() never runs and the inflater's native memory is not freed. The advisory says this can end in an off-heap OutOfMemoryError.
- Trigger: Send many requests with Content-Encoding: gzip and a gzipped body to a handler behind GzipHandler, where the response is not gzip-encoded (for example a small or non-compressible response). Then watch native memory and the count of Inflater objects. Advisory workaround: disable GzipHandler.
- Issue: https://github.com/jetty/jetty.project/issues/14260 (closed Jan 5, 2026; the title is the generic 'Improve GZIP performance'). Advisory: https://github.com/jetty/jetty.project/security/advisories/GHSA-xxh7-fcf3-rj7f
- Fix: https://github.com/jetty/jetty.project/pull/14262 (merged to jetty-12.1.x, merge commit a9e1643304cba5cd99a5bb1aba968bf675809226). 12.0 backport: https://github.com/jetty/jetty.project/pull/14261
- Last version with the leak: jetty-12.0.31 (release page exists, commit 5eb4a85cac542a4ad1f2b9d761f9c99f5ca9476e). The advisory lists 12.0.0 to 12.0.31 and 12.1.0 to 12.1.5 as affected.
- First fixed version: jetty-12.0.32 (release page exists, commit f13f7f3ceda880938728d2378d201a661f2a9204). Advisory patched versions: 12.0.32 and 12.1.6.
- Why it fits: Per-request native-memory leak in the project's own code, triggered by a repeated HTTP request with Content-Encoding: gzip when the response is not deflated. Needs no cluster or long uptime. Maven build, with a server runnable in-process.
- Build and run: Maven (README: mvn -Pfast clean install). Tests are JUnit. Jetty runs in-process, so no database or broker is needed. A harness would start an embedded Server with GzipHandler and drive it with an HTTP client.
- Researcher's caveats: The PR and issue title and the 12.0.32 release notes say 'Improve GZIP performance', not 'leak'. The advisory page still says 'No patches yet' and links no fix PR or commit. I read the leak description only from the advisory. I did not open the PR diff, so I could not confirm that #14262 or #14261 contain the destroy() or callback change. The mapping of the leak to those PRs is inferred from the advisory's linked issue #14260 and the patched versions. The Jetty tag names (jetty-12.0.31, jetty-12.0.32) were confirmed only from release pages. Release years were not shown on the pages.
- Checker's corrections: 1) The trigger condition is narrower than the candidate states: the request must carry Content-Encoding: gzip and the client must NOT accept gzip responses (no Accept-Encoding: gzip), so the response is not deflated. A "small or non-compressible response" is not what the advisory describes. 2) The advisory's description still says "No patches yet", but its version fields list the patched versions. 3) The leak is in the inflater pool/lifecycle (inflaters never returned to the pool, native memory held), and a 12.0 backport (#14261) also exists. 4) The leak fix is PR #14261 for 12.0 and #14262 for 12.1, both titled "Fixes #14260 - Improve GZIP performance". Both PRs are confirmed to carry the destroy() callback change; I read the diff for #14261. 5) Some third-party CVE sites give conflicting affected/fixed ranges (for example "12.0.31/12.1.0"); the GitHub advisory is authoritative.
- Practical notes: I did not verify any build details; the points below are not from sources I checked. Jetty 12.0.x is, to my knowledge, a Java 17 baseline (12.1.x is 17+ too). It is a large multi-module Maven build, so use mvn -Pfast clean install (skips tests), or build only the jetty-server module with -pl jetty-core/jetty-server -am. A full test run is slow, so avoid it. The leak test is in-process: start an embedded Server with GzipHandler, send many POSTs with Content-Encoding: gzip, a gzipped body and no Accept-Encoding, then watch the inflater pool in-use count or the number of live Inflater objects. The in-use count stays nonzero on 12.0.31 and returns to 0 on 12.0.32. No external services are needed. The sandbox needs access to Maven Central and github.com to fetch dependencies and tags. Native memory growth is slow per request, so counting Inflater instances or checking pool state is a more reliable signal than RSS.

### Spring Framework: ResponseEntity return values retained in ResolvableType cache (gh-28232) (known leak, confidence medium)
- Repository: https://github.com/spring-projects/spring-framework (Very high: core Spring project. I did not read the star count on the repo page.)
- Leak (heap (cached MethodParameter retains the actual return value)): ReturnValueMethodParameter in HandlerMethod stored the actual return value. When Spring HATEOAS passed it to ResolvableType#forMethodParameter, the static ResolvableType.cache (a ConcurrentReferenceHashMap) kept the value alive. The reporter saw response bodies accumulating as different APIs were called.
- Trigger: Call controller methods whose return value is wrapped as a ReturnValueMethodParameter and then resolved through ResolvableType.forMethodParameter. The report involves Spring HATEOAS, so the test or harness would likely need spring-hateoas on the classpath. This path is not confirmed by me. Then measure heap growth from retained response objects.
- Issue: https://github.com/spring-projects/spring-framework/issues/28232 (closed Apr 8, 2022). Backport: https://github.com/spring-projects/spring-framework/issues/28273 (milestone 5.2.21).
- Fix: https://github.com/spring-projects/spring-framework/commit/eefdd2c768cbacdc97839ede2209a630cf1f0d3e (message 'Avoid return value reference in potentially cached MethodParameter instance', Closes gh-28232). A second commit also references the issue: 5cbf85a6f81757b95e84a09d676e8a33a2565671.
- Last version with the leak: v5.3.18 (commit 707a24c48b21fc35e8be715afc80f020a24a9714). See caveats: this is inferred, not proven.
- First fixed version: v5.3.19 (commit cedb5874b72c3311c8c6e2f03a53537590f2e0dc). Its release notes list #28232 as a bug fix.
- Why it fits: Heap leak in the project's own code (spring-web and spring-messaging HandlerMethod), triggered by repeated handler invocations. The fix is a 10-line change, so the diff is easy to compare against a detector's finding.
- Build and run: Gradle (the repo wrapper). Tests are JUnit and run in-process with no external services.
- Researcher's caveats: The issue gives no formal reproduction, only screenshots of the retention path that I could not see. The commit diff adds no tests. I did not confirm that v5.3.18 contains the leak. Its release notes do not list #28232, and the issue's Affects field says 5.2.8, so v5.3.18 is the last 5.3.x tag before the fix only by inference from the milestone. The leak may need Spring HATEOAS to surface, which may make a pure Spring Framework test loop miss it. Release dates on the tag pages had no year.
- Checker's corrections: Popularity: about 60.3k stars and 38.8k forks. Release years: 5.3.18 is Mar 31 2022 and 5.3.19 is Apr 13 2022. The issue's Affects field is 5.2.8, so the leak predates 5.3.x; v5.3.18 is a reasonable affected ref but not formally proven to contain the leak. Pre-fix parent of eefdd2c on main is 9f91168 (backport parent is 69c7eb9). Nothing else in the candidate needs correcting.
- Practical notes: Caveats stand. There is no formal reproduction, only the report with screenshots. A pure-framework harness can likely reproduce it without HATEOAS: build a HandlerMethod, call getReturnValueType(largeObject), pass the result to ResolvableType.forMethodParameter, drop the object, GC, and check whether it is still reachable via the static cache. That is my inference and I did not run it. The fix is tiny, so the detector's finding is easy to compare against the diff. Build is the Gradle wrapper. I did not verify the JDK for 5.3.18 and 5.3.19, so check the build files at that tag. A full Gradle build of Spring Framework is large (many modules, several GB of dependencies, long first build), so build only spring-web and spring-messaging with their dependencies. Tests are in-process JUnit and need no external services, but the first Gradle run needs network access to download dependencies. I only read web pages and did not check the build or the test machine.

### Apache Log4j 2: LogBuilder ThreadLocal leak in the Log4j-to-SLF4J bridge (#3819) (known leak, confidence medium)
- Repository: https://github.com/apache/logging-log4j2 (3.6k GitHub stars (repo page); one of the most widely used Java libraries)
- Leak (thread-local value retained in pooled threads (classloader or class retention on undeploy)): In SLF4JLogger#getLogBuilder, logBuilder.get() ran before the ENABLE_THREADLOCALS check, so the initial SLF4JLogBuilder was stored in the ThreadLocal and never cleared. Tomcat reported a SEVERE checkThreadLocalMapForLeaks warning on undeploy.
- Trigger: Log through a Log4j 2 logger with log4j-to-slf4j in a web app, then undeploy. The reporter used Tomcat 11.0.6 and JDK 21.0.7. A JUnit-style loop would run logging from pool threads inside a child classloader, then drop the classloader and check whether it is collected. This loop is not provided by the project.
- Issue: https://github.com/apache/logging-log4j2/issues/3819 (closed Jul 20, 2025)
- Fix: PR https://github.com/apache/logging-log4j2/pull/3824 (commit 05d97d2, 'fix: Prevent LogBuilder memory leak in Log4j API to Logback bridge')
- Last version with the leak: rel/2.25.1 (release page exists, commit bda63362cf405449ff4edc2e4d92353be65c4d4e). The issue was reported against 2.25.0, and I read nothing showing 2.25.1 changed this.
- First fixed version: rel/2.25.2 (release page exists, commit 6923bd90cbbbbe4d7e5e99013097559ba6228b73; its notes list 'Fix potential memory leak involving LogBuilder in Log4j API to Logback bridge', #3819 and #3824). The issue milestone also lists 2.26.0.
- Why it fits: Leak in the project's own code: a ThreadLocal is populated even when Constants.ENABLE_THREADLOCALS is false, as it is in web applications. It holds a value in pool threads and can pin the webapp classloader. The fix is a small gate behind the flag.
- Build and run: Maven (mvnw wrapper). Tests are JUnit, with modules such as log4j-api-test and log4j-core-test. I did not read the build instructions in BUILDING.adoc. External services should not be needed for the relevant module, but I did not verify this.
- Researcher's caveats: This is a classloader or thread-local leak that shows on undeploy, so it is harder to trigger from plain repeated test runs than a per-request leak. It is the weakest of the three for an automated heap-growth loop. The same pattern was fixed earlier in the core library: LOG4J2-3657, fixed in 2.21.0, https://issues.apache.org/jira/browse/LOG4J2-3657 (Jira only, no GitHub PR link found). A harness that reproduces it by stopping and starting Jetty in a JUnit loop is described by the reporter there. The affected_ref of rel/2.25.1 is inferred, not confirmed. Commit 05d97d2 is a short hash from the issue page; I did not open the PR.
- Checker's corrections: Fix commit full hash is 05d97d2ac1ed51b071541d53b7e18b8852d4c18a; PR merge commit on 2.x is 2c66a74; the pre-fix parent commit is 8ec5703. Milestones are 2.25.2 and 2.26.0. rel/2.25.1 as affected ref is inferred from release notes, not confirmed by a repro. The PR already includes a unit test (SLF4JLoggerTest) that checks the ThreadLocal via reflection.
